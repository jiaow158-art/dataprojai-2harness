# DeepSeek Harness（dsh）引擎接入设计

> 日期：2026-09-07 · 版本：v2（按审阅意见重写：报告执行、安全边界、故障恢复、验收方式）
> 状态：已与用户逐节确认，v2 待复审
> 阶段：第一阶段（先证明能力不退化，再做服务化稳定）

**核心命题：换底盘，不减能力。** 先证明 dsh 能完整接住 Claude Code 现在做的全部工作，再解决服务化运行的稳定性。不趁换引擎重构报告系统、权限体系或平台。

---

## 1. 背景与动机

当前问数系统的 agent 引擎是 Claude Code（claudecodeui 后台 headless 调用）。DeepSeek Harness（`dsh`）已开源（MIT，Cordis 插件体系：工具/命令/skill/hook/MCP/模型皆插件，官方支持 Web UI / Headless / SDK 场景）。以 dsh 取代 Claude 的动机（用户确认，四条全选）：

1. **数据主权/私有化** —— 阶段一先用 DeepSeek API，自托管权重留作演进（dsh 模型适配器可插拔）
2. **成本压力** —— DeepSeek API 成本远低于 Claude
3. **供应商锁定** —— Claude 彻底退出运行时；且架构要允许"将来别的引擎再取代 dsh"
4. **产品化** —— 系统要散发给外部用户使用，闭源引擎 + 每客户 Anthropic API 依赖不可交付

**关键认知**：本项目最值钱的资产（Layer 2 语义层 + Layer 3 Skills + Layer 4 Eval + MCP server）本就是模型无关的 markdown/Python。换引擎是"换底盘"，不是重做系统。

## 2. 目标与非目标

### 目标（第一阶段交付物）

1. **能力不退化**：dsh 完整复现现有系统全部能力——问数、动态报告生成（含 Python/Shell 执行）、多轮追问——以"现有能力迁移清单"逐项验收
2. **服务化稳定**：任务排队与隔离、断线重连、阶段化故障自恢复（用户无需重新提问或手动接续）
3. **评测放行**：66 场景对照人工确认的标准答案判分，能力清单 + 重复回归 + 故障测试 + 并发提交测试全部达标
4. **内部白名单试点**：在明确数据授权范围内开放给指定员工，真实任务持续验证

### 非目标（明确排除）

- **不重构报告系统**为固定模板服务——先原样迁移现有报告生成方式，后续依稳定性数据决定哪些步骤固化
- **不做细粒度数据权限**（RLS/过滤视图/角色组合）——用户已明确"按账号角色区分，具体先放着"，另列后续工作；本阶段只守第 7 节三项最低条件
- 不自托管模型权重（仅留 `DSH_BASE_URL` 配置口）
- 不做多租户/授权计费等产品化基础设施（阶段二）
- 不修改 skill 知识内容（metrics.md、决策树、陷阱库一字不改，只适配加载机制）
- Claude 不进运行时，仅以试点期回滚开关形式短暂存在（M4 移除）

## 3. 关键决策记录

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| D1 | 方案选型 | 网关 + 可插拔 BackendProvider，单一 DshBackend | 同时满足"去 Claude 化"与"未来引擎可再替换" |
| D2 | Claude 的居所 | 只存在于开发环境，不进运行时 | 用户明确：dsh 是取代，不是并列 |
| D3 | 报告能力 | **保留 Python/Shell 执行**，通过受控执行工具进隔离环境；不禁止代码执行，只禁止无边界执行 | 现有报告依赖 Agent 写 HTML + 调 Python/Shell，禁止即切断能力；同时改引擎又改报告机制，出错无法归因 |
| D4 | 凭据分离 | 脚本执行环境与持有 DWS/模型密钥的服务环境物理分开；生成脚本只拿本次任务必要的数据文件 | "工作目录不同"不等于隔离；dsh 沙箱策略只覆盖文件操作，不表达网络/进程/系统调用/凭据限制 |
| D5 | 数据权限 | 细化暂缓；守住三底线：试点范围明确、运行账号与管理账号分开、身份与数据归属链路保留 | 用户明确"具体先放着"；暂缓的是细粒度建设，不是放弃基本访问边界 |
| D6 | 故障处理 | 任务恢复要求（阶段化自动恢复 + 保存点续跑），不只是重试次数 | 用户核心产品要求："不能中途报错"——区分"工具执行出错"与"用户任务最终失败" |
| D7 | 并发模型 | 最多 10 人同时提交，实际并行由工作进程池控制（2~3 起步压测），其余排队；同会话问题串行 | "承接 10 人提交"≠"同时全速跑 10 套完整 Agent"；响应时间暂不作首要指标 |
| D8 | 超时架构 | 分层保护上限：单 SQL/单脚本/单 API 调用各自设限 + 整任务总预算；不用固定 300s 一刀切 | 复杂报告耗时不均，平顶超时会误杀长任务 |
| D9 | 评测判分 | 对照人工确认的标准答案做业务正确性判分（指标/维度/时间/组织范围/单位），加能力完整性清单，作为放行条件 | 已有标准答案就该真用；"SQL 可执行+行数符合"不足以证明能力不退化 |
| D10 | 重复回归 | 至少连续 3 轮回归全过才放行 | 避免单次侥幸通过 |
| D11 | 稳定性承诺口径 | 验收标准是"零未恢复失败"，不承诺外部依赖永久零故障 | 稳定性靠故障测试证明，不靠隐藏报错 |
| D12 | M0 内容 | 完整能力验证（复杂报告在最终受限环境端到端复现），不只是 skill 加载 + MCP 调用 | 最关键风险——"能否完整生成原来的报告"——必须最先验证 |

## 4. 总体架构

```
┌─────────────────────────┐
│  claudecodeui (Web层)    │  现有，小改：调用地址换成网关
│  /opt/claudecodeui      │  （用户认证唯一入口 + 断线重连/进度状态展示）
└───────────┬─────────────┘
            │ HTTP + SSE（内网，Bearer token + user + scope_group）
            ▼
┌──────────────────────────────────────────────────────┐
│  engine-gateway（新，Node/TypeScript）                 │
│  任务编排 · 持久化任务记录 · 工作进程池/排队 · 限流      │
│  阶段化故障恢复 · 审计日志 · 报告发布检查                │
│  ┌────────────────────────────────────────┐           │
│  │ BackendProvider 接口（可插拔契约）         │           │
│  │   ▲ 实现                                │           │
│  │   └─ DshBackend（当前唯一引擎）           │           │
│  └────────────────────────────────────────┘           │
└───────┬──────────────────────────────┬────────────────┘
        │ 服务环境（持有 DWS 凭据 + 模型密钥）│ 任务数据文件单向送入
        ▼                              ▼
┌──────────────────────┐   ┌──────────────────────────┐
│ dsh headless 会话     │   │ 脚本执行环境（无凭据）      │
│ + DeepSeek-V4 API    │   │ 受控执行工具拉起生成的      │
│ + skill 插件         │   │ Python/Shell，只拿到      │
│ + MCP 桥接 ──▶       │   │ 本次任务的查询结果文件      │
│   dws_mcp_server.py  │   │ 和工作目录，无DB无网络      │
└─────────┬────────────┘   └──────────────────────────┘
          │ MCP stdio（受限只读账号）
          ▼
   DWS GaussDB
```

**换引擎的承接点**：`BackendProvider` 接口 + 第 5 节规范事件是稳定契约。将来新引擎 = 新写一个实现 + 改一行注册配置，Web 层与 API 协议零改动。

**凭据分离原则（D4）**：dsh/MCP 所在的服务环境持有 DWS 凭据与模型密钥；生成的 Python/Shell 脚本在独立的无凭据环境执行，通过文件拿到已保存的查询结果——不把数据库密码交给生成的脚本，也不依赖 dsh 的 workspace 沙箱（其策略范围只覆盖文件操作，不表达网络/进程/系统调用/凭据限制）。

### 单元职责边界

| 单元 | 做什么 | 不做什么 |
|---|---|---|
| engine-gateway | 任务接收/排队/编排、持久化任务记录、阶段化恢复、限流审计、报告发布检查 | 不解析业务语义、不碰 SQL |
| DshBackend | dsh 会话管理、事件归一化、超时取消、保存点记录 | 不 fork dsh，只用官方扩展点 |
| 受控执行工具（新 dsh 工具插件） | 在无凭据隔离环境执行生成的 Python/Shell，回传产物 | 不透传任何服务环境凭据、默认无网络 |
| dws_mcp_server.py | 4 个只读工具（受限运行账号） | 不给生成脚本直连数据库的任何途径 |
| run_agent_eval.py | 经网关跑 66 场景、对照标准答案判分、失败分类 | 不直接调引擎（与线上同路径） |

## 5. 网关 API 与任务模型

### 端点

| 端点 | 用途 |
|---|---|
| `POST /api/tasks` | 提交任务 `{question, session_id?, user, scope_group}` → `{run_id}` |
| `GET /api/tasks/{run_id}` | 状态查询（阶段、进度、终态、失败原因） |
| `GET /api/tasks/{run_id}/events` | SSE 进度流，支持 `Last-Event-ID` 断线续传 |
| `GET /api/health` | 存活探查 |

### 任务模型

- 每个提问 = 一个任务，有独立 `run_id`；一个多轮会话（session_id）下可以有多个任务
- **同会话任务串行执行**：后一问在前一问完成后才开跑，避免读到不完整上下文
- 任务流水线与恢复回路：

```
接收 → 排队 → 分析/查询 → 脚本执行 → 报告检查 → 发布 → 完成
                    ↘ 有限修复/重试（按第 9 节阶段化策略）↗
```

### 任务持久化（网关不再是纯 SSE 转发）

网关落盘保存（轻量本地存储，选型在实施计划定，默认 SQLite）：

- 任务状态机（当前阶段、重试计数、预算消耗）
- 会话历史（dsh 会话转录，供续跑与新尝试重建上下文）
- 已成功的查询结果（SQL + 结果集文件——脚本执行环境的数据来源）
- 报告产物与发布状态
- 审计记录：user / scope_group / question / 全部 SQL / 耗时 / token / 终态

### 规范事件（稳定契约）

```
event: stage    → {"stage": "queued|analyzing|querying|script_running|report_checking|repairing|publishing", "text": "..."}
event: sql      → {"sql": "SELECT...", "rows": 42, "elapsed_ms": 1200}
event: answer   → {"markdown": "## 结论..."}
event: report   → {"path": "reports/{user}/xxx.html"}             发布后才有此事件
event: error    → {"code": "TIMEOUT|ENGINE_ERROR|CONFIG|RATE_LIMIT|UNRECOVERABLE", "message": "..."}
event: done     → {"run_id": "...", "engine": "dsh", "elapsed_ms": ..., "tokens": {...}, "recovered": true|false}
```

前端据此显示"正在查询""正在修复报告""正在重新连接"等状态，恢复期间不呈现为卡死。

### 配置（env，不进代码）

```
GATEWAY_PORT / AUTH_TOKEN
DSH_API_KEY / DSH_MODEL=deepseek-v4 / DSH_BASE_URL
SKILLS_DIR=../skills
MAX_CONCURRENT_TASKS=3        # 工作进程池大小（压测起点，非容量结论）
MAX_QUEUE / RATE_LIMIT_QPM / RATE_LIMIT_CONCURRENCY
SQL_TIMEOUT_S=30              # 单条 SQL 保护上限（MCP 侧 statement_timeout）
SCRIPT_TIMEOUT_S              # 单次脚本执行上限
API_CALL_TIMEOUT_S            # 单次模型接口调用上限
TASK_BUDGET_S                 # 整任务总执行预算（复杂报告允许更长，不搞平顶300s）
MAX_REPAIR_ROUNDS             # 每阶段修复/重试上限
DWS_RUN_ACCOUNT_*             # 受限只读运行账号（非管理账号）
```

## 6. 安全边界：受控执行，而非禁止执行

### 原则

不是"不允许执行代码"，而是"**允许完成业务所需的代码执行，但不能在宿主机上无边界地执行**"。第一阶段原样迁移现有报告生成方式（Agent 写 HTML、调 Python/Shell），不强行重构为固定模板服务——同时改引擎和报告机制，出问题无法归因。

### 能力与边界

| 能力 | 第一阶段边界 |
|---|---|
| 读取 Skills、引用文件、模板 | 保留；知识和模板目录只读 |
| 创建、修改 HTML 和 Python 脚本 | 保留；只能写入当前任务的工作目录 |
| 执行 Python/Shell | 保留；通过受控执行工具进入无凭据隔离环境 |
| 查询 DWS | 继续走 MCP（受限只读账号）；生成的脚本拿不到数据库密码，只用已保存的查询结果文件 |
| 发布报告 | 先生成临时产物，检查通过后再发布到 `reports/{user}/` |

### 两个执行环境的隔离（不依赖 dsh 沙箱自证）

- **服务环境**：网关 + dsh 会话 + MCP server，持有 DWS 凭据与模型密钥
- **脚本执行环境**：受控执行工具拉起生成的脚本，只拿到本次任务的查询结果文件与工作目录；环境变量清洗（无任何凭据）、默认无网络、有资源上限
- dsh 官方沙箱服务的策略范围主要是文件操作，不表达网络/进程/系统调用/凭据限制——因此**不能凭启用 workspace-write 就认定隔离完成**，隔离由上述双环境拆分实现并在 M0 验证

### 运行环境在部署时准备，不靠 Agent 临时修

M0 盘点现有报告脚本实际依赖的 Python 包、字体、图表资源、目录和命令，形成部署清单——运行环境在部署时装好，而不是每次用户提问时让 Agent 现场装依赖。

### 其余安全对策（保留）

| 威胁 | 对策 |
|---|---|
| 提示注入诱导越权 | 域边界规则（skill 内置）+ 工具边界（脚本环境无凭据无网络，注入无可乘之机） |
| 恶意问题打爆资源 | 按 user 限流 + 任务预算 + 脚本资源上限 |
| 报告 HTML 藏脚本 | 发布前检查 + 静态托管加 CSP；ECharts 本地引用是模板约定 |
| 串看他人报告 | `reports/{user}/` 属主校验 |
| 出事无法追责 | 审计日志（第 5 节） |

## 7. 数据权限：暂缓细化，守住最低边界

四维权限（职级/公司/数据域/事业部）与 RLS/过滤视图/角色组合的具体方案**另列后续工作，本阶段不建设**。第一阶段只守三项最低条件：

1. **试点范围明确**：只开放给指定内部员工，且这些员工确实有权查看试点开放的数据——不因"内部员工"默认全员全量权限
2. **运行账号与管理账号分开**：管理/配置用现有管理账号；问数服务使用独立的受限只读账号，MCP 与 Agent 环境不出现管理凭据
3. **身份和数据归属保留**：持续记录 user、session_id 与预留的 scope_group；会话、任务、报告全部可关联到用户。后续扩展角色权限时不必重补这条链路

暂缓的是细粒度权限建设，不是放弃基本访问边界。

## 8. DshBackend 适配细节

### 8.1 Skill 格式兼容 —— 第一个实施动作是 spike，不是开发

现有 13 个 skill 为 Claude Code 格式（SKILL.md frontmatter + body + references/ + templates/）。dsh skill 是 Cordis 插件，格式细节需实测：

| spike 结果 | 应对 |
|---|---|
| 直接读 SKILL.md 格式 | 零成本，skills/ 保持单一样本源 |
| 格式小差异（frontmatter 字段名等） | 转换脚本 `skills/ → build/dsh-skills/`，部署时跑，源头一份 |
| 插件 API 完全不同 | 只适配加载机制，skill 正文内容一字不改 |

### 8.2 MCP 桥接

- `dsh-mcp-client` 以 stdio 拉起 `dws_mcp_server.py`，每任务一个 MCP 进程
- 连接使用**受限只读运行账号**（第 7 节），凭据只在服务环境 env
- 4 个工具（run_query / list_tables / describe_table / search_tables）原样暴露；run_query 保持 SELECT-only + LIMIT 200 + statement_timeout
- 修复现状：本仓库 .mcp.json 的 args 指向旧目录 `D:\dataprojai\dws_mcp_server.py` 绝对路径，改为仓库内相对引用

### 8.3 模型接入

```
DSH_MODEL_ADAPTER=deepseek-api / DSH_API_KEY / DSH_MODEL=deepseek-v4
# 自托管演进：DSH_BASE_URL=http://vllm内网地址:8000  ← 只改这一行
```

### 8.4 工具集（含受控执行）

dsh 插件注册配置加载：skill 插件（skills/ 只读）+ MCP 桥接（4 工具）+ **受控执行工具**（自研插件：把生成的 Python/Shell 送进无凭据隔离环境执行，回传 stdout/stderr/产物）。除此之外不注册任意文件系统、任意 shell、网络访问插件——Agent 能执行的代码只能经受控执行工具走，边界在第 6 节。

### 8.5 会话、保存点与事件归一化

- 每任务独立 dsh 会话，cwd = 任务工作目录（知识只读 + 本任务可写 + 查询结果文件）
- dsh 原生事件 → 第 5 节规范事件，映射集中在 DshBackend
- 按第 9 节记录保存点；超时/取消走 `cancel()` + 进程级兜底

### 8.6 知识路由不受影响

域边界规则（只答 6 个已覆盖域）写在 Knowledge skill 内容里，随 skill 原样迁移——引擎换了，纪律不换。

## 9. 任务恢复与稳定性（核心产品要求）

### 要求表述

> 对于可恢复的模型、查询、脚本和报告生成故障，系统应自动恢复，不要求用户重新组织问题或手动接续；恢复失败时，保留任务记录和必要上下文，明确告知结果，**不得伪装成功**。

区分"**工具执行发生错误**"与"**用户的任务最终失败**"：内部可以发现错误、自我修正，但不做一半就把问题甩给用户。

### 阶段化恢复策略

| 出问题的位置 | 处理方式 |
|---|---|
| 模型接口短暂网络异常 | 保留必要上下文的前提下有限重试 |
| SQL 执行失败 | 错误交给 Agent 修正；限定纠错次数与执行预算 |
| 查询成功但 Python 脚本失败 | **复用本次已保存的查询结果**，修复脚本重跑；不默认重新查数 |
| HTML 已生成但图表/资源异常 | 修复、重新检查；不把残缺报告当成功发布 |
| 浏览器刷新/连接断开 | 任务状态仍可查询，重连后恢复进度展示（`Last-Event-ID`），任务不丢失 |
| 凭据无效/持续不可用/权限不足 | **停止无效重试**，明确记录失败原因；不靠重试绕权限或掩盖故障 |

### 恢复机制边界

- **不要求 dsh 从任意内部推理位置原地续接**。先实现业务阶段恢复：持久化会话历史、已成功查询结果、任务状态、报告产物（第 5 节）；引擎不能原地续接时，用这些保存点**启动新的执行尝试**（携带已有上下文与结果），而不是从零重来
- 每阶段修复/重试有上限（`MAX_REPAIR_ROUNDS`），超限进入明确失败终态（UNRECOVERABLE），保留全部记录

### 稳定性承诺口径

验收标准是"**预设可恢复故障零未恢复失败**"；不承诺外部 API、数据库、服务器永久零故障。稳定性最终靠故障注入测试证明，不靠隐藏报错实现。

## 10. 并发与容量

- **提交与执行分离**：允许最多 10 人同时提交任务；实际并行数由工作进程池控制（`MAX_CONCURRENT_TASKS`，2~3 起步压测），其余排队且能看到真实排队状态
- 容量数字是**试验起点，不是已验证结论**：依内存、数据库连接、脚本执行与模型接口表现逐步调整
- **同会话串行**：见第 5 节任务模型
- 超时架构：分层保护上限（单 SQL / 单脚本 / 单 API 调用）+ 整任务总预算（`TASK_BUDGET_S`），不用固定 300s 平顶限制
- 第一阶段验证重点：不同用户不串数据；一个任务失败不拖垮其他任务；任务结束后进程与连接正确释放；排队用户看到真实状态
- 并发测试画像：**连续多批次**，混合简单问数、复杂报告、多轮追问与故障恢复任务——不是十个简单问题同时跑通一次就算

## 11. 评测与放行

### 11.1 业务正确性：66 场景对照标准答案

`run_agent_eval.py` 经网关发送自然语言问题（与线上同路径），判分对照人工确认的标准答案：

- 除行数外，核对**关键指标（金额/数量/占比/排序/单位）、维度、时间范围、组织范围**，以及最终回答与报告内容
- 固定数据快照或可复现的数据范围；数值误差规则预先定义
- 不要求 SQL 字符串一致，要求业务结果正确；不要求 HTML 逐字一致，要求报告信息、图表对应关系与现有交互能力不退化
- 66 场景全部满足已确认标准答案；**已有例外单独记录，不临时降低门槛**

失败自动分类（定位改进方向）：表选错 / 口径错 / 执行错 / 日期格式错 / 超预算 / 域外误答 / 指标数值偏差 / 报告内容缺失。

### 11.2 能力完整性：现有能力迁移清单

`capability_checklist.md` 从**当前系统实际功能和执行轨迹**整理（不只看 13 个 skill 能否加载）：skill 正文引用的 references/templates 资源加载、MCP 4 工具、Python/Shell 受控执行、动态报告产物、多轮会话——每项独立验收，无遗漏、无功能缩水。

### 11.3 放行标准

| 项目 | 标准 |
|---|---|
| 66 个既定业务场景 | 全部满足已确认标准答案；已有例外单独记录，不临时降门槛 |
| 现有能力清单 | 每项有对应测试，无遗漏、无功能缩水 |
| 重复运行 | 至少连续 3 轮回归通过 |
| 报告检查 | 文件可打开、资源可加载、表格与图表数据一致、不存在串用户产物 |
| 故障恢复 | 预设可恢复故障全部自动处理；不可恢复故障有明确终态和完整记录 |
| 10 人同时提交 | 无任务无故丢失、无会话串线、无单任务拖垮服务 |

（以上是写入计划的验收条件，不是对当前实现的达标判断。）

## 12. 里程碑

| 阶段 | 重点 | 放行条件 |
|---|---|---|
| **M0 完整能力验证** | 选取代表性复杂报告，在**最终受控环境**跑通全链路：Skills → MCP → Python/Shell（受控执行）→ HTML → 多轮追问；同步盘点报告脚本的依赖环境（Python 包/字体/图表资源/目录/命令），形成部署清单 | 关键链路完整成功，不靠临时开放宿主机权限 |
| **M1 服务化与恢复** | 网关、任务持久化、会话续接、排队、分类重试、报告发布检查、前端状态 | 出现可恢复故障时，用户无需手动接续 |
| **M2 迁移回归** | 66 场景标准答案判分、能力清单、≥3 轮重复回归、故障注入测试、10 人提交测试 | 正确性、功能完整性和稳定性均达标（第 11.3 节） |
| **M3 内部白名单试点** | 在明确数据授权范围内开放给指定员工（第 7 节三底线） | 真实任务持续验证；所有失败可追踪、可复现 |
| **M4 稳定与收尾** | 修复试点问题，形成运行规范；满足退出条件后移除旧引擎回滚路径 | 完成正式切换；细粒度角色权限另列后续工作 |

**现在最先推进的**：不是完整网关开发，也不是权限——拿一份当前最复杂、且已能正确生成的报告，让 dsh 在最终受限环境里完整复现（M0 核心）。这一步通过，才证明"换底盘、不减能力"有可执行基础；随后再用任务恢复、排队和评测把它做稳。
