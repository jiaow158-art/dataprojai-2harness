# DeepSeek Harness（dsh）引擎接入设计

> 日期：2026-09-07 · v3 修订：2026-09-08（第二轮审阅：结果双通道、三层会话模型、幂等与接管规则、隔离具体化、模型定版）
> 状态：已与用户逐节确认，v3 待复审
> 阶段：第一阶段（先证明能力不退化，再做服务化稳定）

**核心命题：换底盘，不减能力。** 先证明 dsh 能完整接住 Claude Code 现在做的全部工作，再解决服务化运行的稳定性。不趁换引擎重构报告系统、权限体系或平台。

---

## 1. 背景与动机

当前问数系统的 agent 引擎是 Claude Code（claudecodeui 后台 headless 调用）。DeepSeek Harness（`dsh`）已开源（MIT，Cordis 插件体系：工具/命令/skill/hook/MCP/模型皆插件，官方支持 Web UI / Headless / SDK 场景）。以 dsh 取代 Claude 的动机（用户确认，四条全选）：

1. **数据主权/私有化** —— 阶段一先用 DeepSeek API，自托管权重留作演进（预留接入配置）
2. **成本压力** —— DeepSeek API 成本远低于 Claude
3. **供应商锁定** —— Claude 彻底退出运行时；且架构要允许"将来别的引擎再取代 dsh"
4. **产品化** —— 系统要散发给外部用户使用，闭源引擎 + 每客户 Anthropic API 依赖不可交付

**关键认知**：本项目最值钱的资产（Layer 2 语义层 + Layer 3 Skills + Layer 4 Eval + MCP server）本就是模型无关的 markdown/Python。换引擎是"换底盘"，不是重做系统。

## 2. 目标与非目标

### 目标（第一阶段交付物）

1. **能力不退化**：dsh 完整复现现有系统全部能力——问数、动态报告生成（含 Python/Shell 执行）、多轮追问（口径与结果引用正确延续）——以"现有能力迁移清单"逐项验收
2. **服务化稳定**：任务排队与隔离、断线重连、阶段化故障自恢复、幂等与接管（用户无需重新提问或手动接续）
3. **评测放行**：66 场景对照人工确认的标准答案判分，能力清单 + 重复回归 + 故障测试 + 并发提交测试全部达标
4. **内部白名单试点**：在明确数据授权范围内开放给指定员工，真实任务持续验证

### 非目标（明确排除）

- **不重构报告系统**为固定模板服务——先原样迁移现有报告生成方式，后续依稳定性数据决定哪些步骤固化
- **不做细粒度数据权限**（RLS/过滤视图/角色组合）——用户已明确"按账号角色区分，具体先放着"，另列后续工作；本阶段只守第 7 节三项最低条件
- 不自托管模型权重（预留接入配置；实际切换需验证模型接口、工具调用与流式事件兼容性，不提前保证"只改一行"）
- 不做多租户/授权计费等产品化基础设施（阶段二）
- 不改 skill 业务口径；执行适配优先放在适配层——发现正文依赖旧工具或路径时，单列兼容问题处理，不直接认定"加载成功即迁移成功"
- Claude 不进运行时：dsh 服务不做单任务跨引擎兜底；试点期间保留**部署级**旧版本回滚，M4 移除

## 3. 关键决策记录

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| D1 | 方案选型 | 网关 + 可插拔 BackendProvider，单一 DshBackend | 同时满足"去 Claude 化"与"未来引擎可再替换" |
| D2 | Claude 的居所 | 只存在于开发环境；dsh 服务不做单任务跨引擎兜底，试点期保留部署级旧版本回滚，M4 移除 | 用户明确：dsh 是取代，不是并列；部署级回滚是过渡期运维手段，不是引擎兜底 |
| D3 | 报告能力 | 保留 Python/Shell 执行，通过受控执行工具进独立受控执行环境；不禁止代码执行，只禁止无边界执行 | 现有报告依赖 Agent 写 HTML + 调 Python/Shell；同时改引擎又改报告机制，出错无法归因 |
| D4 | 凭据分离 | 脚本在独立受控执行环境中运行（不要求两台机器），服务环境凭据不进入脚本环境；生成脚本只拿本次任务必要的数据文件 | "工作目录不同"不等于隔离；dsh 沙箱策略只覆盖文件操作，不表达网络/进程/系统调用/凭据限制 |
| D5 | 数据权限 | 细化暂缓；守住三底线：试点范围明确、运行账号与管理账号分开、身份与数据归属链路保留 | 用户明确"具体先放着"；暂缓的是细粒度建设，不是放弃基本访问边界 |
| D6 | 故障处理 | 任务恢复要求（阶段化自动恢复 + 保存点续跑 + 幂等/接管/单次发布），不只是重试次数 | 用户核心产品要求："不能中途报错"——区分"工具执行出错"与"用户任务最终失败" |
| D7 | 并发模型 | 最多 10 人同时提交，实际并行由工作进程池控制（2~3 起步压测），其余排队；同会话问题串行 | "承接 10 人提交"≠"同时全速跑 10 套完整 Agent"；响应时间暂不作首要指标 |
| D8 | 超时架构 | 分层保护上限：单 SQL/单脚本/单 API 调用各自设限 + 整任务总预算；不用固定 300s 一刀切 | 复杂报告耗时不均，平顶超时会误杀长任务 |
| D9 | 评测判分 | 对照人工确认的标准答案做业务正确性判分（指标/维度/时间/组织范围/单位），加能力完整性清单，作为放行条件 | 已有标准答案就该真用；"SQL 可执行+行数符合"不足以证明能力不退化 |
| D10 | 重复回归 | 至少连续 3 轮**真实执行**回归全过才放行（不得命中缓存；每轮记录版本五元组，中途改实现则重新计数） | 避免单次侥幸通过，也避免缓存造成的假通过 |
| D11 | 稳定性承诺口径 | 验收标准是"零未恢复失败"，不承诺外部依赖永久零故障 | 稳定性靠故障测试证明，不靠隐藏报错实现 |
| D12 | M0 内容 | 完整能力验证（复杂报告在最终受控环境端到端复现 + 隔离配置落地 + 依赖盘点），不只是 skill 加载 + MCP 调用 | 最关键风险——"能否完整生成原来的报告"——必须最先验证 |
| D13 | 结果双通道 | 模型可见预览（≤200 行）与脚本使用数据集分离：可信查询结果层保存实际执行查询的完整结果（标注实际行数/是否完整/是否截断/结果引用）；超数据量预算走 SQL 重聚合或受控分批，不得把截断数据当完整数据生成报告 | 800 行被截成 200 行后 Python 照样算出"完整"合计——不报错的错报告比显式报错更危险 |
| D14 | 三层会话模型 | session_id=逻辑对话，run_id=任务，dsh 会话=执行实例；任务**出队执行时**装载该对话最新已提交历史、已确认口径与获准引用的结果，再创建执行实例；受控结果引用，不开放上一问工作目录的任意读写 | 历史在提交时提前固定会导致连续两问时第二问读不到第一问刚完成的结果 |
| D15 | 幂等与接管 | 提交去重（唯一提交标识→原 run_id）、执行尝试编号（旧实例失权才开新尝试）、报告单次发布（恢复后先查发布记录）、SSE 事件递增编号可重放、终态区分成功/失败/取消 | 恢复机制本身不能引入重复提交/重复执行/重复发布；单服务+SQLite+少量工作进程即可实现，不引入分布式调度 |
| D16 | 模型定版 | `deepseek-v4-flash`（用户 2026-09-07 暂定；官方 API 模型 ID，非内部别名），`deepseek-v4-pro` 为能力不足时的备选，切换需重跑回归 | 与官方 API 文档列出的具体模型名对齐，不使用文档外别名 |

## 4. 总体架构

```
┌─────────────────────────┐
│  claudecodeui (Web层)    │  保留现有页面，适配任务型协议（提交/状态/事件/断线恢复）；
│  /opt/claudecodeui      │  改动范围在 M0 对接验证后确定（用户认证唯一入口）
└───────────┬─────────────┘
            │ HTTP + SSE（内网，Bearer token + user + scope_group）
            ▼
┌──────────────────────────────────────────────────────┐
│  engine-gateway（新，Node/TypeScript）                 │
│  任务编排 · 持久化任务记录 · 工作进程池/排队 · 限流      │
│  阶段化故障恢复 · 幂等与接管 · 审计日志 · 报告发布检查    │
│  ┌────────────────────────────────────────┐           │
│  │ BackendProvider 接口（可插拔契约）         │           │
│  │   ▲ 实现                                │           │
│  │   └─ DshBackend（当前唯一引擎）           │           │
│  └────────────────────────────────────────┘           │
│  可信查询结果层：保存实际执行查询的完整结果文件            │
│  （行数/完整性/截断标注 + 结果引用ID）                   │
└───────┬──────────────────────────────┬────────────────┘
        │ 服务环境（持有 DWS 凭据 + 模型密钥）│ 结果文件按任务单向送入
        ▼                              ▼
┌──────────────────────┐   ┌──────────────────────────┐
│ dsh headless 会话     │   │ 独立受控执行环境（无凭据）  │
│ （执行实例）           │   │ 受控执行工具拉起生成的      │
│ + deepseek-v4-flash  │   │ Python/Shell，只拿到      │
│ + skill 插件         │   │ 结果引用文件和工作目录，    │
│ + MCP 桥接 ──▶       │   │ 无DB凭据、默认无网络       │
│   dws_mcp_server.py  │   └──────────────────────────┘
└─────────┬────────────┘
          │ MCP stdio（受限只读账号；预览≤200行+结果引用）
          ▼
   DWS GaussDB
```

**换引擎的承接点**：`BackendProvider` 接口 + 第 5 节规范事件是稳定契约。将来新引擎 = 新写一个实现 + 改一行注册配置，Web 层与 API 协议零改动。

**凭据分离原则（D4）**：dsh/MCP 所在的服务环境持有 DWS 凭据与模型密钥；生成的 Python/Shell 脚本在**独立受控执行环境**中执行（不要求两台机器，具体隔离配置见第 6.2 节），通过结果引用文件拿到已保存的查询结果——不把数据库密码交给生成的脚本，也不依赖 dsh 的 workspace 沙箱（其策略范围只覆盖文件操作，不表达网络/进程/系统调用/凭据限制）。

### 单元职责边界

| 单元 | 做什么 | 不做什么 |
|---|---|---|
| engine-gateway | 任务接收/去重/排队/编排、持久化任务记录与事件重放、阶段化恢复、限流审计、报告发布检查 | 不解析业务语义、不碰 SQL |
| 可信查询结果层 | 保存实际执行查询的完整结果文件（行数/完整性/截断标注/引用ID） | 不让模型抄写结果、不为存文件重跑 SQL |
| DshBackend | dsh 会话管理、事件归一化、超时取消、保存点与执行尝试记录 | 不 fork dsh，只用官方扩展点 |
| 受控执行工具（新 dsh 工具插件） | 在无凭据隔离环境执行生成的 Python/Shell，回传产物；覆盖报告全操作环（读资源/建改脚本/执行/查输出/读错误/取产物） | 不透传任何服务环境凭据、默认无网络 |

## 5. 网关 API 与任务模型

### 端点

| 端点 | 用途 |
|---|---|
| `POST /api/tasks` | 提交任务 → `{run_id, session_id}`；携带唯一提交标识用于去重 |
| `GET /api/tasks/{run_id}` | 状态查询（阶段、进度、终态、失败原因） |
| `GET /api/tasks/{run_id}/events` | SSE 进度流；事件带递增编号，服务端保存可重放记录，前端按编号去重（不只是 Last-Event-ID） |
| `GET /api/health` | 存活探查 |

### 请求

```json
POST /api/tasks
Authorization: Bearer <内网token>
{
  "question": "2024年Q3瓷砖事业部库存跌价TOP10",
  "session_id": "可选；首次创建逻辑对话时由服务端返回",
  "user": "zhangsan",
  "scope_group": "reserved",
  "client_submission_id": "前端生成的唯一提交标识，重试时复用"
}
```

`user` 由 claudecodeui 可信后端从登录身份生成，网关不信任浏览器直传的用户名；`scope_group` 为预留字段（第 7 节）。

### 三层会话模型（D14）

- **session_id** = 用户的逻辑对话；**run_id** = 一次提问任务；**dsh 会话** = 具体执行实例
- 首次提交创建逻辑对话，同时返回 session_id 与 run_id；一个逻辑对话下可有多个任务，**同会话任务串行执行**
- 任务**出队开始执行时**（而非提交排队时）装载：该对话最新已提交的历史、已确认的业务口径、获准引用的查询结果与报告——然后创建 dsh 执行实例。历史在执行时读取，保证连续两问时第二问能读到第一问刚完成的结果
- **受控结果引用**：允许引用上一问的结果 ≠ 允许任意读写上一问的工作目录；只传递受控结果引用；失败尝试的临时文件不自动成为后续对话的可信依据

### 任务流水线（主要阶段，非不可回退的固定顺序）

```
接收 → 排队 → 分析/查询 → 脚本执行 → 报告检查 → 发布 → 完成
                    ↘ 有限修复/重试（按第 9 节阶段化策略）↗
```

流水线是主要路径而非单向闸门：报告检查发现缺少必要指标时，允许经 MCP 补查再重新生成报告；"复用已成功查询结果"不能理解成"进入脚本阶段后永远不能查新数据"。

### 任务持久化（网关不再是纯 SSE 转发）

网关落盘保存（轻量本地存储，默认 SQLite，选型在实施计划定）：

- 任务状态机（当前阶段、执行尝试编号、重试计数、预算消耗、终态：**成功/失败/取消三者明确区分**）
- 会话历史（供续跑与新执行实例重建上下文）
- **可信查询结果**：实际执行查询的完整结果文件 + 元数据（实际行数、是否完整、是否截断、结果引用ID）——脚本执行环境的数据来源
- 报告产物与**发布记录**（恢复时先查发布记录，防重复发布/半成品覆盖成功产物）
- 事件重放日志（递增编号）
- 审计记录：user / scope_group / question / 全部 SQL / 耗时 / token / 终态

### 结果双通道（D13）

- **模型预览**：run_query 返回给模型的结果 ≤200 行，附结果引用（引用ID、实际行数、是否截断）
- **脚本数据集**：可信查询结果层保存**实际执行查询的完整结果**，直接来自该次执行——不让模型重新抄写结果，也不为保存文件再无条件执行一次 SQL
- 超过数据量预算时：SQL 内重新聚合，或受控分批获取；**不得将截断数据默认为完整数据生成报告**
- 脚本不直连数据库，MCP 边界不变

### 规范事件（稳定契约）

```
event: stage    → {"stage": "queued|analyzing|querying|script_running|report_checking|repairing|publishing", "text": "..."}
event: sql      → {"sql": "SELECT...", "rows": 42, "truncated": false, "result_ref": "r-0001", "elapsed_ms": 1200}
event: answer   → {"markdown": "## 结论..."}
event: report   → {"path": "reports/{user}/xxx.html"}             发布后才有此事件
event: error    → {"code": "TIMEOUT|ENGINE_ERROR|CONFIG|RATE_LIMIT|UNRECOVERABLE", "message": "..."}
event: done     → {"run_id": "...", "status": "succeeded|failed|cancelled", "engine": "dsh",
                   "elapsed_ms": ..., "tokens": {...}, "recovered": true|false}
```

- done 必须带明确 `status`，不能只发耗时/token 让前端猜结果
- 内部可恢复错误通过 `repairing` 阶段展示，不让前端误判整个任务已失败

### 配置（env，不进代码）

```
GATEWAY_PORT / AUTH_TOKEN
DSH_API_KEY / DSH_MODEL=deepseek-v4-flash / DSH_BASE_URL
SKILLS_DIR=../skills
MAX_CONCURRENT_TASKS=3        # 工作进程池大小（压测起点，非容量结论）
MAX_QUEUE / RATE_LIMIT_QPM / RATE_LIMIT_CONCURRENCY
SQL_TIMEOUT_S=30              # 单条 SQL 保护上限（MCP 侧 statement_timeout）
SCRIPT_TIMEOUT_S              # 单次脚本执行上限
API_CALL_TIMEOUT_S            # 单次模型接口调用上限
TASK_BUDGET_S                 # 整任务总执行预算（复杂报告允许更长，不搞平顶300s）
MAX_REPAIR_ROUNDS             # 每阶段修复/重试上限
RESULT_PREVIEW_ROWS=200       # 模型预览行数上限
RESULT_DATA_BUDGET_ROWS       # 单结果集数据量预算（超过走重聚合/分批）
DWS_RUN_ACCOUNT_*             # 受限只读运行账号（非管理账号）
```

## 6. 安全边界：受控执行，而非禁止执行

### 6.1 原则与能力边界

不是"不允许执行代码"，而是"**允许完成业务所需的代码执行，但不能在宿主机上无边界地执行**"。第一阶段原样迁移现有报告生成方式，不强行重构为固定模板服务。

| 能力 | 第一阶段边界 |
|---|---|
| 读取 Skills、引用文件、模板 | 保留；知识和模板目录只读 |
| 创建、修改 HTML 和 Python 脚本 | 保留；只能写入当前任务的工作目录 |
| 执行 Python/Shell | 保留；通过受控执行工具进入独立受控执行环境 |
| 查询 DWS | 继续走 MCP（受限只读账号）；生成的脚本拿不到数据库密码，只用结果引用文件 |
| 发布报告 | 先生成临时产物，检查通过后再发布到 `reports/{user}/` |

### 6.2 隔离配置：M0 必须产出实际可运行的配置

不停留在"无凭据、无网络、有上限"的描述，M0 落地并验证：

- **隔离方式**：选型并写明（容器/受限子进程+清洗环境，实施计划定，M0 验证）
- **执行身份**：脚本以什么系统身份运行（非服务进程身份、非 root）
- **目录挂载**：哪些目录只读（知识/模板/结果引用）、哪个可写（任务工作目录），白名单外不可见
- **资源上限**：CPU/内存/磁盘/进程数上限，超时后子进程树的清理方式（不留孤儿进程）
- **网络**：默认无网络；如个别报告步骤确需外联，逐项登记放行，不开全局

### 6.3 威胁 → 对策

| 威胁 | 对策 |
|---|---|
| 提示注入诱导越权 | 脚本环境的凭据、网络和文件边界用于**限制代码执行风险**；提示注入仍可能影响查询选择、业务口径与报告内容，需通过工具授权及对抗测试验证（与 dsh 官方安全声明一致：沙箱只能降低风险，不是唯一安全控制） |
| 恶意问题打爆资源 | 按 user 限流 + 任务预算 + 脚本资源上限 |
| 越权访问他人数据 | **属主校验覆盖全操作**：提交到已有会话、查看任务、订阅事件流、读取报告；user 由 claudecodeui 可信后端从登录身份生成，不信浏览器直传 |
| 报告 HTML 藏脚本 | 发布前检查 + 静态托管 CSP；**CSP 不作为唯一 XSS 防线**（OWASP）——报告在最终展示环境中的资源加载与交互脚本策略单独验证（见 6.4） |
| 串看他人报告 | `reports/{user}/` 属主校验 |
| 出事无法追责 | 审计日志（第 5 节） |

### 6.4 报告展示环境单独验证

脚本环境无网络 ≠ 用户浏览器打开 HTML 后也受限。现有动态报告在最终展示环境中须验证：既能正常交互（图表/联动），也不能触及不该访问的资源。不要求重构为固定模板，只要求在真实展示环境下用对抗用例证明。

### 6.5 运行环境在部署时准备

M0 盘点现有报告脚本实际依赖的 Python 包、字体、图表资源、目录和命令，形成部署清单——运行环境在部署时装好，而不是每次用户提问时让 Agent 现场装依赖。

## 7. 数据权限：暂缓细化，守住最低边界

四维权限（职级/公司/数据域/事业部）与 RLS/过滤视图/角色组合的具体方案**另列后续工作，本阶段不建设**。第一阶段只守三项最低条件：

1. **试点范围明确**：只开放给指定内部员工，且这些员工确实有权查看试点开放的数据——不因"内部员工"默认全员全量权限
2. **运行账号与管理账号分开**：管理/配置用现有管理账号；问数服务使用独立的受限只读账号，MCP 与 Agent 环境不出现管理凭据
3. **身份和数据归属保留**：持续记录 user、session_id 与预留的 scope_group；会话、任务、报告全部可关联到用户。后续扩展角色权限时不必重补这条链路

暂缓的是细粒度权限建设，不是放弃基本访问边界（含第 6.3 节的全操作属主校验与可信身份生成）。

## 8. DshBackend 适配细节

### 8.1 Skill 格式兼容 —— 第一个实施动作是 spike，不是开发

现有 13 个 skill 为 Claude Code 格式（SKILL.md frontmatter + body + references/ + templates/）。dsh skill 是 Cordis 插件，格式细节需实测：

| spike 结果 | 应对 |
|---|---|
| 直接读 SKILL.md 格式 | 零成本，skills/ 保持单一样本源 |
| 格式小差异（frontmatter 字段名等） | 转换脚本 `skills/ → build/dsh-skills/`，部署时跑，源头一份 |
| 插件 API 完全不同 | 只适配加载机制，业务口径不变 |

**兼容问题单列**：skill 正文若引用旧工具名、执行路径或资源定位方式，作为独立兼容问题记录处理；不认定"加载成功即迁移成功"。

### 8.2 MCP 桥接与结果双通道

- `dsh-mcp-client` 以 stdio 拉起 `dws_mcp_server.py`，每任务一个 MCP 进程
- 连接使用**受限只读运行账号**（第 7 节），凭据只在服务环境 env
- 4 个工具原样暴露；**run_query 双通道输出**：完整结果由可信查询结果层落盘（第 5 节），模型收到 ≤200 行预览 + 结果引用（实际行数/是否截断）；statement_timeout 保持
- 修复现状：本仓库 .mcp.json 的 args 指向旧目录 `D:\dataprojai\dws_mcp_server.py` 绝对路径，改为仓库内相对引用

### 8.3 模型接入

```
DSH_MODEL=deepseek-v4-flash   # 官方 API 模型 ID（2026-09-07 用户暂定）
# 备选：deepseek-v4-pro——能力不足时切换，切换后必须重跑回归
# 自托管演进：预留 DSH_BASE_URL 接入配置；实际切换需验证模型接口、工具调用与流式事件兼容性
```

### 8.4 工具集（含受控执行）

dsh 插件注册配置加载：skill 插件（skills/ 只读）+ MCP 桥接（4 工具）+ **受控执行工具**（自研插件：把生成的 Python/Shell 送进独立受控执行环境执行，回传 stdout/stderr/产物）。除此之外不注册任意文件系统、任意 shell、网络访问插件——Agent 能执行的代码只能经受控执行工具走。

**M0 验证工具清单的完整性**：受控工具须完整支持现有报告的操作环——读取引用资源、创建/修改脚本、执行、检查输出、读取错误、取回产物——不能只验证"能执行一段 Python"。

### 8.5 会话、保存点与事件归一化

- 按第 5 节三层模型：任务出队执行时装载对话历史与获准引用的结果，创建 dsh 执行实例（cwd = 任务工作目录：知识只读 + 本任务可写 + 结果引用文件）
- dsh 原生事件 → 第 5 节规范事件，映射集中在 DshBackend
- 按第 9 节记录保存点与执行尝试编号；超时/取消走 `cancel()` + 进程级兜底

### 8.6 知识路由不受影响

域边界规则（只答 6 个已覆盖域）写在 Knowledge skill 内容里，随 skill 原样迁移——引擎换了，纪律不换。

## 9. 任务恢复与稳定性（核心产品要求）

### 要求表述

> 对于可恢复的模型、查询、脚本和报告生成故障，系统应自动恢复，不要求用户重新组织问题或手动接续；恢复失败时，保留任务记录和必要上下文，明确告知结果，**不得伪装成功**。

区分"**工具执行发生错误**"与"**用户的任务最终失败**"：内部可以发现错误、自我修正，但不做一半就把问题甩给用户。

### 阶段化恢复策略

| 出问题的位置 | 处理方式 |
|---|---|
| 模型接口短暂网络异常 | 保留必要上下文的前提下有限重试 |
| SQL 执行失败 | 错误交给 Agent 修正；限定纠错次数与执行预算 |
| 查询成功但 Python 脚本失败 | **复用本次已保存的查询结果**，修复脚本重跑；不默认重新查数（补查新数据不受此限，见第 5 节流水线说明） |
| HTML 已生成但图表/资源异常 | 修复、重新检查；不把残缺报告当成功发布 |
| 浏览器刷新/连接断开 | 任务状态仍可查询，重连后按事件编号恢复进度展示，任务不丢失 |
| 凭据无效/持续不可用/权限不足 | **停止无效重试**，明确记录失败原因；不靠重试绕权限或掩盖故障 |

### 幂等、接管与发布规则（D15）

| 场景 | 规则 |
|---|---|
| 网关已接收任务但提交响应丢失，前端再次提交 | 用 `client_submission_id` 去重，返回原 run_id，不创建新任务 |
| 执行进程退出，需要接管任务 | 记录执行尝试编号；确认旧执行实例已结束或失去执行权后才开始新尝试——不允许两个实例同时处理同一任务 |
| 报告已发布但任务尚未记为完成时服务中断 | 恢复后先检查发布记录，不重复发布、不用半成品覆盖成功产物 |
| SSE 断线后重连 | 事件递增编号 + 服务端可重放记录；前端按编号去重 |
| 任务最终失败或被取消 | 终态明确区分成功/失败/取消；done 事件带 `status`；内部可恢复错误经 `repairing` 阶段展示 |

以上规则在单服务 + SQLite + 少量工作进程的方案内实现，**不因加了恢复机制就引入分布式调度系统**。

### 恢复机制边界

- **不要求 dsh 从任意内部推理位置原地续接**。先实现业务阶段恢复：持久化会话历史、可信查询结果、任务状态、报告产物（第 5 节）；引擎不能原地续接时，用这些保存点**启动新的执行尝试**（携带已有上下文与结果），而不是从零重来
- 每阶段修复/重试有上限（`MAX_REPAIR_ROUNDS`），超限进入明确失败终态（UNRECOVERABLE），保留全部记录

### 稳定性承诺口径

验收标准是"**预设可恢复故障零未恢复失败**"；不承诺外部 API、数据库、服务器永久零故障。稳定性最终靠故障注入测试证明，不靠隐藏报错实现。

## 10. 并发与容量

- **提交与执行分离**：允许最多 10 人同时提交任务；实际并行数由工作进程池控制（`MAX_CONCURRENT_TASKS`，2~3 起步压测），其余排队且能看到真实排队状态
- 容量数字是**试验起点，不是已验证结论**：依内存、数据库连接、脚本执行与模型接口表现逐步调整
- **同会话串行**：见第 5 节三层会话模型
- 超时架构：分层保护上限（单 SQL / 单脚本 / 单 API 调用）+ 整任务总预算（`TASK_BUDGET_S`），不用固定 300s 平顶限制
- 第一阶段验证重点：不同用户不串数据；一个任务失败不拖垮其他任务；任务结束后进程与连接正确释放；排队用户看到真实状态
- 并发测试画像：**连续多批次**，混合简单问数、复杂报告、多轮追问与故障恢复任务——不是十个简单问题同时跑通一次就算

## 11. 评测与放行

### 11.1 业务正确性：66 场景对照标准答案

`run_agent_eval.py` 经网关发送自然语言问题（与线上同路径），判分对照人工确认的标准答案：

- 除行数外，核对**关键指标（金额/数量/占比/排序/单位）、维度、时间范围、组织范围**，以及最终回答与报告内容
- 固定数据快照或可复现的数据范围；数值误差规则预先定义
- 不要求 SQL 字符串一致，要求业务结果正确；不要求 HTML 逐字一致，要求报告信息、图表对应关系与现有交互能力不退化
- 66 场景全部满足已确认标准答案；**已有例外单独记录，不临时降低门槛**

失败自动分类（定位改进方向）：表选错 / 口径错 / 执行错 / 日期格式错 / 超预算 / 域外误答 / 指标数值偏差 / 报告内容缺失 / **数据截断（无提示不完整）**。

### 11.2 能力完整性：现有能力迁移清单

`capability_checklist.md` 从**当前系统实际功能和执行轨迹**整理（不只看 13 个 skill 能否加载）：skill 正文引用的 references/templates 资源加载、MCP 4 工具、Python/Shell 受控执行（完整操作环）、动态报告产物、多轮会话（口径与结果引用延续）——每项独立验收，无遗漏、无功能缩水。

### 11.3 回归与报告检查的执行说明

- **三轮回归必须是三轮真实执行**，不得命中上一轮任务结果缓存。每轮记录：代码版本、dsh 版本、Skills 版本、模型配置、数据范围与评测数据版本。中途修改了影响结果的实现，连续通过轮次**重新计数**
- **报告正确性独立检查**：不以"Agent 说报告完成"或"HTML 能打开"为准；从最终产物中核对关键指标与图表数据，与标准答案或可信结果比较

### 11.4 固定测试用例（每类对应一个已识别缺口）

| 用例 | 要证明的事情 |
|---|---|
| 查询结果超过 200 行的真实报告 | 不发生无提示的数据截断（合计/占比/图表对得上完整数据） |
| 同一会话连续追问并生成报告 | 上下文、口径和结果引用正确延续（时间/组织范围/指标口径不漂移） |
| 提交响应丢失后重试、SSE 断线重连 | 不重复创建任务，进度可恢复 |
| 工作进程退出、发布前后中断 | 能接管任务，不重复发布成功报告 |
| 跨用户访问任务或会话、脚本越界、恶意报告内容 | 基础隔离真实生效，而不只是正常流程跑通 |

### 11.5 放行标准

| 项目 | 标准 |
|---|---|
| 66 个既定业务场景 | 全部满足已确认标准答案；已有例外单独记录，不临时降门槛 |
| 现有能力清单 | 每项有对应测试，无遗漏、无功能缩水 |
| 重复运行 | 至少连续 3 轮真实执行回归通过（11.3 规则） |
| 报告检查 | 文件可打开、资源可加载、表格与图表数据一致、不存在串用户产物（独立核对） |
| 故障恢复 | 预设可恢复故障全部自动处理；不可恢复故障有明确终态和完整记录 |
| 10 人同时提交 | 无任务无故丢失、无会话串线、无单任务拖垮服务 |

| A5 | deepseek-v4-flash 在 agentic SQL + 动态报告任务上的能力未经本数据集验证——M2 门槛即为此设；备选 deepseek-v4-pro 切换需重跑回归 | 已被流程覆盖（待测试验证） |
| A6 | 现状待办：仓库 .mcp.json 指向旧目录绝对路径，M0/M1 期间修复 | 待办 |
| A7 | "零未恢复失败"依赖故障注入用例设计质量——预设故障集必须覆盖第 9 节全部阶段 | 已被流程覆盖（待测试验证） |
| A8 | **dsh 软件成熟度**：官方标记为实验性开发者预览，明确说明尚未接受安全审计、不应视为生产就绪。不阻碍 M0 验证，但 M3 试点需明确风险接受范围、固定 dsh 版本并留存安全验证证据；业务场景通过不等于可以正式上线 | 已知风险，需管理层知情接受 |
