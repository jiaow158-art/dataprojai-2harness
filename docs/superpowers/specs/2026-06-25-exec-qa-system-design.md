## 1. 背景与目标

### 1.1 背景

`dataproj` 已实现 Anthropic 4 层 Agentic Analytics Stack：

| 层 | 内容 |
|---|---|
| Data Foundations | DWS（GaussDB），`dm` / `dwrfin` 主用 |
| Sources of Truth | 业绩域 7 份 reference（`metrics.md` 经 6/10 + 6/18 两轮审计，ME1-ME3 模式错误已抽象成规则） |
| Skills | `sales-performance-knowledge` + `sales-performance-analyst`（6 步法含对抗性审查） |
| Validation | `eval_dataset.json` 30 场景，业绩域 ~10 条 |

`webapp/`（v0.1 MVP）已交付：FastAPI + Vue 暗色聊天 UI，6 步工作流（理解→选表→SQL→执行→解读→审查），DeepSeek-V4 跑 SQL 生成，4 大防幻觉补丁固化，session 多轮对话，自动生成 ECharts 报告。

**当前 webapp 准确率约 83%（业绩域 eval），单问延迟 30-60s。**

### 1.2 目标（本次设计）

将业绩域 webapp 从"分析师工具"升级为"集团 C-Level 决策助手"。即：

1. **答案形态**从 Markdown 长文 → 结构化卡片（TL;DR + KPI + 归因 + 建议 + 溯源）
2. **答案深度**从描述性（"是什么"）→ 诊断性（"为什么"）→ 处方性（"怎么办"，**预审模板**填充）
3. **信任护栏**从可选 → 强制（COUNT 验证、数据时效水印、审计日志、失败升级）
4. **对比语境**从用户主动问 → 任何数字自动配同比/环比/目标/排名

### 1.3 已确定的 4 个架构决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 目标用户 | 集团 C-Level（1-3 人：总裁/CEO/CFO） | 不需要 RBAC，但需要高信任 + 全集团视角 |
| 运行模式 | 被动问答为主（升级现有 webapp） | 不引入调度/推送/异常检测的复杂度 |
| 答案深度 | 决策建议（含归因） | C-Level 要"怎么办"，不只"是什么" |
| 建议来源 | 预审模板库（业务专家维护） | LLM 不发明建议，避免给 C-Level 错误行动 |

### 1.4 非目标（本次明确不做）

- ❌ **早会简报 push / 异常告警**：用户选了被动问答模式
- ❌ **多轮澄清状态机**：用户选了直接答（保留现有简单 follow-up 即可）
- ❌ **RBAC / SSO**：1-3 个 C-Level，内网访问即可
- ❌ **覆盖其他 21 个域**：明确仅业绩域（瓷砖/卫浴/国际营销中心/丽适岩板/公司层面 5 大事业部）
- ❌ **语音输入**：P4 之后再考虑

## 2. 现状诊断：8 个 Gap

| # | 维度 | 现状 | C-Level 需要 | 严重度 |
|---|---|---|---|---|
| G1 | 答案形态 | Markdown + iframe | 3 句结论 + KPI 卡 + 归因 + 建议 | 🔴 致命 |
| G2 | 对比语境 | 用户问同比才有 | 任何数字自动配同比/环比/目标/排名 | 🔴 致命 |
| G3 | 信任护栏 | ME2「伪 1 行 NULL」会让 LLM 基于空数据编结论 | 强制 COUNT 验证 + 失败升级 | 🔴 致命 |
| G4 | 数据时效 | 藏在脚注 | 顶部水印"数据截至 YYYY-MM-DD HH:MM" | 🟠 高 |
| G5 | 归因能力 | 无 | 自动拆解到渠道/区域/产品 | 🔴 致命 |
| G6 | 决策建议 | 无 | 模板库匹配 + 数据填充 | 🔴 致命 |
| G7 | 审计/溯源 | 脚注里有 | 顶部 badge + 完整审计日志 | 🟠 高 |
| G8 | 业务事件 | 无 | 春节/政策/调整 → 异常归因兜底 | 🟡 中 |

**附加风险**：当前 webapp 用 DeepSeek-V4，但 Skills 为 Claude 设计。模型差异是质量天花板，G3/G5/G6 都依赖强推理。P2 启动前需做 A/B 测：同 10 问跑 DeepSeek vs Claude Sonnet 4.6，准确率差 ≥5pct 则切 Claude。

### 三个不能省的非功能性能力

1. **强制 COUNT 验证**：每条 SQL 在 SUM 之前先 `SELECT COUNT(*) WHERE ...`，0 行直接抛 `NoDataError` → 返回"该筛选条件下无数据"。这是 ME2「伪 1 行 NULL」的根治方案。
2. **数据时效水印**：每次答案顶部显示。C-Level 必须知道这是"昨天"还是"上月"。
3. **审计日志**：每次问数留底（问题/SQL/答案/置信度/是否审核通过/时间戳）。C-Level 场景必须，出了问题能复盘。

## 4. 分阶段路线图

总周期 **12 周主线 + 持续治理**，每 Phase 独立可演示、独立可回滚。

### Phase 1 — MVP（4 周）

**前端改造（`webapp/static/index.html`）**
- 聊天 UI → "答案卡片" UI：5 个区块（TL;DR / KPI 卡 / 数据明细表 / 溯源 / 操作按钮）
- 顶部常驻"数据时效水印"（取自 `dw_last_update_date`）
- "👍/👎"反馈按钮（点 👎 进 eval 队列）

**后端改造（`webapp/orchestrator/workflow.py`）**
- 6 步保留，**3 处增强**：
  - **step4 加 COUNT 预检**：执行 SQL 前，对同 WHERE 条件先跑 `COUNT(*)`；0 行直接抛 `NoDataError` → 返回"该筛选条件下无数据"
  - **step5 INTERPRET_PROMPT 改造**：强制输出"3 句结论 + KPI 卡 JSON + 明细表"。KPI 卡必须含同比/环比/目标/排名（4 个对比语境都缺时主动说"无对比数据"）
  - **新增 step5.5 自检**：检查数字量级（瓷砖月业绩应 3-5 亿、达成率 0-150% 等），异常直接标注"⚠️ 数值偏离常识"
- 新增 `webapp/audit_log.py`：每次问数写一行 JSON 到 `webapp/audit/{YYYY-MM-DD}.jsonl`

**Knowledge 改动**（业绩域）
- `metrics.md` 顶部加「数据时效」段：每张表的 `dw_last_update_date` 取值规则
- 暂不加新 reference 文件（归因/建议模板在 P2/P3 加）

**显式不做**
- ❌ 归因拆解（P2）  ❌ 决策建议（P3）  ❌ 移动端（P4）  ❌ 个性化默认视图（P4）

**Phase 1 成功标准**
- C-Level 用 10 个高频问题测，准确率 ≥95%（当前 ~83%）
- 单问端到端延迟 < 15s（当前 30-60s）
- `eval_dataset.json` 业绩域场景从 ~10 → 25 条

### Phase 2 — 归因引擎（4 周）

**核心交付**：自动拆解"为什么"到渠道/区域/产品维度。

**Knowledge 新增**：`skills/sales-performance-knowledge/references/attribution-templates.md`（5-8 棵归因树）

| 归因树 | 触发场景 | 拆解维度 |
|---|---|---|
| ATT-达成落后 | 达成率 < 目标 - 5pct | 事业部 → 渠道 → 区域 → 产品品牌 |
| ATT-同比异常 | 同比 ≤ -10% | 事业部 → 渠道 → TOP3 客户 |
| ATT-渠道结构变化 | TOP1 渠道占比变动 ≥5pct | 渠道 → 子渠道 → 产品 |
| ATT-区域异常 | 某区域同比 ±15% | 区域 → 省份 → 城市 → 客户 |
| ATT-高值占比下降 | 高值产品占比同比下降 | 事业部 → 产品品牌 → 系列 |
| ATT-大规格下滑 | 大规格销量同比 -10% | 工厂 → 产品品牌 → 规格 |
| ATT-预算偏离 | 实际 vs 预算差 ≥10% | 月度 → 事业部 → 渠道 |
| ATT-目标不达标 | 任一事业部达成 < 80% | 事业部 → 渠道 → 区域 |

**工作流改造**：step5 后插入 step5.5 归因拆解——读 `attribution-templates.md` 选模板，跑拆解 SQL，生成归因树 JSON。

**模型决策点**：P2 启动前必须做 DeepSeek vs Claude Sonnet 4.6 的 A/B 测（同 10 个归因问题），如准确率差 ≥5pct 则切 Claude。

**Phase 2 成功标准**
- 归因准确率（人工评判）≥85%
- 归因树点击展开率 ≥50%（C-Level 实际在下钻）

### Phase 3 — 决策建议（4 周）

**核心交付**：场景匹配 + 预审建议填充。

**Knowledge 新增**：`skills/sales-performance-knowledge/references/recommendation-templates.md`

**模板结构（YAML 示例）**

```yaml
- id: TMPL001
  scene: 达成落后 + 工程渠道拖累
  trigger:
    metric: 达成率
    condition: 达成率 < 目标 - 5pct
    attribution_match: 工程渠道贡献 ≤ -3pct
  diagnosis_template: "本月{division}达成{actual}%，低于目标{gap}pct；工程渠道拖累{impact}pct"
  recommendations:
    - text: "{worst_channel}渠道重点项目复盘（建议负责人：{channel_head}）"
      action_type: 复盘
      owner_role: 渠道负责人
    - text: "关注 TOP3 客户提货节奏"
      action_type: 客户跟进
      owner_role: 大客户经理
  confidence_rule:
    require_fields: [last_year_*, integrate_channel, customer]
    min_sample_size: 100
  reviewer: 销售运营总监  # 业务专家审核签字
  approved_at: 2026-XX-XX
```

**业务专家共建**：锁定 1 名销售运营总监 + 1 名财经平台总监，预计投入 6 周（每周 4-6 小时）。共建 20-30 个高频场景模板。

**工作流改造**：step5.5 后插入 step5.7 场景匹配——读 `recommendation-templates.md`，按 trigger 匹配模板，填充数据。LLM 仅做"场景匹配 + 数据填充"，**不发明建议**。

**模板库后台 UI**（`webapp/admin/templates.html`）：业务专家不用直接改 markdown，表单式编辑。

**Phase 3 成功标准**
- 高频场景模板覆盖率 ≥80%（10 个 C-Level 常问场景命中至少 8 个）
- 建议采纳率（C-Level 在 👍/👎 中点 👍 或行动）≥60%

### Phase 4 — 治理与扩展（持续）

**核心交付**：
- 移动端 H5（响应式 + 触控优化）
- 反馈通道闭环（👎 进 eval 队列，定期 review 入库）
- eval_dataset.json 持续扩充到 100+ 场景
- 模板库后台 UI 完善
- 监控（延迟、错误率、模板命中率、模型成本）

## 5. 关键风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| DeepSeek-V4 推理能力不够支撑归因/建议 | P2/P3 准确率不达标 | P2 启动前 A/B 测：DeepSeek vs Claude Sonnet 4.6；差 ≥5pct 则切 Claude |
| 业务专家投入度不足（P3 需要） | P3 卡住 | P1 阶段就锁定专家档期，演示版先行；模板库后台降低维护门槛 |
| 数据时效水印如果数据未及时更新 | C-Level 失信 | 水印 +"数据滞后告警"（超过 3 天未更新主动标红） |
| 移动端开发资源（P4） | P4 延期 | P4 可独立排期，不阻塞 P1-P3 |
| 模板匹配率不足（P3 上线初期） | 建议缺失率高 | P3 前先跑 1 周"无建议版"收集 C-Level 实际问题，再排模板优先级 |
| 强制 COUNT 验证增加延迟 | P1 延迟难达标 | COUNT 走索引，正常 <500ms；可与大查询并行 |
