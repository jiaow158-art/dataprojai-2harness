### 2.3 未达标项分析

**延迟未达 ≤45s 目标**（实测 avg 64s）：
- step1+2 合并确实省了 ~12s（85 → 64 = -21s 实测改善，略高于预估）
- 但 step3 SQL 生成（DeepSeek-V4 单次 ~15-20s）+ step5 INTERPRET（~15-20s）+ step6 review（~10-15s）= 40-55s 串行下限
- 要破 45s 需要结构化优化：把 step5 + step6 合并、或并行化 review、或换更快的模型（DeepSeek-V4 vs Claude A/B 测是 P2 前置 spike）

## 3. 计划外收获

合并 step1+2 顺带修了 Q9「各事业部预算执行情况」的**错域问题**：
- 基线：路由到 `fin-cost`（"预算"被当成财经域关键词）
- 实测：路由到 `sales-performance`（合并后 prompt 把 metrics.md 直接喂给路由判断，业绩域的 `_ys` 字段被识别为预算语义）
- 这是计划没明确承诺修复的 P1.5 followup（"Router 错域修复"原本不在 scope 内），属于附带改善

## 4. Followup（留给下一轮）

按优先级：

1. **延迟优化（P1.5 followup）**：实测 64s 仍超 ≤45s 目标。下一步候选：
   - 把 step5 INTERPRET 和 step6 review 合并（评测质量影响需 A/B）
   - 用 streaming 改善首字节延迟
   - 切 Claude（spec §5 明确要求 P2 前做 A/B 测）

2. **YoY 强制后处理**：手测 Phase 1 时 2/10 KPI 含 YoY；P1.5 没修。需 INTERPRET_PROMPT 改造 + 后处理补全（如果 SQL 数据有同比字段但 LLM 没填，自动算）。

3. **量级误报（百分比 vs 小数）**：LLM 偶尔把达成率输出为 `74.98`（百分比）而非 `0.7498`（小数），`magnitude_check` 判越界。要么接受 0-150 范围，要么 INTERPRET_PROMPT 强制小数。

4. **DeepSeek vs Claude A/B 测**：spec §5 明确要求 P2 启动前做。10 问 × 2 模型对比准确率 + 延迟。差 ≥5pct 则切 Claude。

5. **C-Level UX 手测**：本次只跑机读指标（NoDataError / 延迟 / KPI 卡）。视觉/交互层（水印颜色、卡片布局、👍/👎 按钮可用性）仍需真人打开浏览器手测。

## 5. 结论

Phase 1.5 spike 状态：**⚠️ 部分达标**

- ✅ **P0-1（NoDataError）完美解决**：2/10 → 0/10，超出 ≤1/10 目标
- ❌ **P0-2（延迟）部分改善**：85s → 64s（-25%），未达 ≤45s 目标；max 延迟从 168s 降到 90s（-46%）
- ✅ **附加修复**：Q9 错域问题顺带修了
- ✅ **不回归**：32/32 pytest 通过，25/25 sales-performance eval 通过

P0-1 是更严重的问题（C-Level 看到"无数据"会立刻弃用），已彻底解决。P0-2 部分改善，主要瓶颈是 DeepSeek-V4 单次推理速度本身——继续优化需要模型切换（spec §5 A/B 测）或工作流结构改造（step5+6 合并），都属于下一轮 spike 范围。

Phase 2 归因引擎可以启动，但建议先做 DeepSeek vs Claude A/B（spec §5 P2 前置 spike），因为归因会引入更多 LLM 调用，延迟和准确率都会受模型选择影响。
